# Firestorm native dependencies and the C++ surface

Source surveyed: `C:\Dev\vkstorm-aleph-ref` (branch `vkstorm-aleph`, Firestorm master as of 2026-10-18). All paths below are relative to that repo root. Line counts were produced with `wc -l` over `*.cpp/*.h/*.inl/*.mm/*.c`, excluding `tests/` directories.

## 0. What "the default release build" means

Firestorm's shipping configuration is `autobuild configure -c ReleaseFS` driven by `scripts/configure_firestorm.sh`, with CI adding `-DUSE_FMODSTUDIO=ON -DUSE_KDU=ON --crashreporting --lto` (`.github/workflows/build_viewer.yml:23`) and, per grid, `-DOPENSIM:BOOL=ON` for OpenSim builds or `-DHAVOK_TPV:BOOL=ON` for Second Life builds (`.github/workflows/build_viewer.yml:165`). Consequences:

- FMOD Studio and Kakadu (KDU) **are** in the shipped SL/OS release builds. `ReleaseFS_open` (no FMOD/KDU) exists as a configuration (`autobuild.xml:3444-3471`) for open-source builders.
- `USE_OPENAL` defaults ON (`indra/cmake/OPENAL.cmake:11`), so both audio backends are compiled; FMOD is instantiated first at runtime when present (`indra/newview/llstartup.cpp:1110`), OpenAL only as fallback (`llstartup.cpp:1122`).
- Havok: `HAVOK_TPV` links the prebuilt closed `llphysicsextensions_tpv` on Windows only (`indra/cmake/LLPhysicsExtensions.cmake:35-45`); on Linux it is forced OFF and VHACD is used (`indra/cmake/Variables.cmake:206-209`); on macOS no TPV library is linked at all (`LLPhysicsExtensions.cmake:37`). Havok and OpenSim support are mutually exclusive (`Variables.cmake:201-212`).
- Crash reporting: `--crashreporting` turns on BugSplat (`scripts/configure_firestorm.sh:538-541`), which replaces the in-tree `llcrashlogger` (`indra/CMakeLists.txt:162-164`).
- Vivox (`slvoice`) is only fetched/packaged when `OPENSIM` is ON (`indra/cmake/ViewerMiscLibs.cmake` `if (OPENSIM) use_prebuilt_binary(slvoice)`; `indra/cmake/Copy3rdPartyLibs.cmake` `if (OPENSIM)` block; `indra/newview/llvoiceclient.cpp:29,133,188`). SL builds use WebRTC voice exclusively.
- Discord: Firestorm ignores LL's `discord_sdk` package and links its own `discord-rpc` unconditionally (`indra/cmake/Discord.cmake:3-33`, `indra/newview/CMakeLists.txt:2658`). `USE_DISCORD` (LL's SDK) is never defined by Firestorm's configure script.
- Growl (GNTP) is linked unconditionally on Windows/macOS (`indra/newview/CMakeLists.txt:2679-2682`); Linux uses libnotify via `dlopen` (`indra/newview/desktopnotifierlinux.cpp:39-60`).
- Velopack installer/updater only with `-DUSE_VELOPACK=ON` (`indra/cmake/Velopack.cmake:3`; CI passes it for Windows/macOS in `.github/workflows/build.yaml:110`).
- Tracy is OFF unless channel starts with "Second Life Test" or `USE_TRACY=ON` (`indra/cmake/Tracy.cmake:7-12`; FS exposes `--tracy`, `configure_firestorm.sh:492`).
- `LL_TESTS` is OFF in FS release configure (`scripts/configure_firestorm.sh:601`).

## 1e. What the current audio engine actually provides (for the spatial-audio decision)

`indra/llaudio/` is 7,641 lines: 2,107 engine + 820 decode manager + 486 vorbis encoder are backend-neutral; FMOD backend 994+136+560 lines; OpenAL backend 737+110 lines.

Engine-level (backend-independent, `indra/llaudio/llaudioengine.h`):
- Fixed pool: `LL_MAX_AUDIO_CHANNELS 30` voices, `LL_MAX_AUDIO_BUFFERS 60` decoded buffers (`llaudioengine.h:57,60`). Channel stealing by priority; priority = gain / max(1, dist^2) to listener (`indra/llaudio/llaudioengine.cpp:1448-1472`), forced priority for UI/preview sounds.
- Sources (`LLAudioSource`, `llaudioengine.h:301-412`): global position (`LLVector3d`) + velocity, gain 0..1, loop, sync master/slave (synchronised loops across objects), queued sounds, per-type secondary gain (SFX/UI/AMBIENT, `llaudioengine.h:79-86`), owner/object IDs for muting, 5 s attached-object timeout.
- Listener (`indra/llaudio/lllistener.h`): position, velocity, up/at orientation, **doppler factor** and **rolloff factor** setters (`lllistener.h:58-59`). The viewer sets doppler = `AUDIO_LEVEL_DOPPLER` and switches rolloff to `AUDIO_LEVEL_UNDERWATER_ROLLOFF` when the camera is under water (`indra/newview/llvieweraudio.cpp:476-486`). Default min distance 2 m (`DEFAULT_MIN_DISTANCE`, `llaudioengine.h:55`); FMOD uses inverse-distance rolloff with `set3DSettings(doppler, 1.0, rolloff)` (`indra/llaudio/lllistener_fmodstudio.cpp:115,122`), right-handed coordinates (`FMOD_INIT_3D_RIGHTHANDED`, `llaudioengine_fmodstudio.cpp:254`).
- Wind: `LLWindGen` (`indra/llaudio/llwindgen.h`) is a procedural resonant-filtered-noise generator producing interleaved stereo; parameters (gain, frequency, pan) are derived from the wind vector relative to the camera (`llaudioengine.cpp:738-800`), lowered to 20 Hz centre under water (`LL_WIND_UNDERWATER_CENTER_FREQ`). FMOD runs it as a custom DSP on the master group (`llaudioengine_fmodstudio.cpp:542-583`); OpenAL streams it through queued buffers on a relative source (`llaudioengine_openal.cpp:508-577`).
- Internet radio: `LLStreamingAudioInterface` (`indra/llaudio/llstreamingaudio.h`) with start/stop/pause/gain/metadata; implemented only for FMOD (ICY/ID3/Vorbis-comment tag parsing `llstreamingaudio_fmodstudio.cpp:201-306`).
- Output device enumeration/selection (FS addition: `getDevices/setDevice`, `llaudioengine.h:198-208`), resampler quality choice (`llaudioengine_fmodstudio.cpp:239-245`).
- Assets: Ogg Vorbis decoded to 16-bit PCM WAV files in the cache by a worker (`llaudiodecodemgr.cpp`), then loaded as whole buffers (`LLAudioBuffer::loadWAV`). No streaming of SL sound assets (they are <= 10 s clips).
- Not provided today: HRTF, reverb/zones, occlusion, per-source cones, sound-asset streaming.

Pure-Rust spatial audio that covers this: `kira` (mixer, tracks, spatial scenes with listener/emitter, distance attenuation, custom effects) or `oddio` (lighter, explicit spatial scene with doppler, HRTF-free panning) over `cpal` for devices; `rodio` for simple playback; `steam-audio-sys` (Valve's Steam Audio, Apache-2.0, binary SDK) for HRTF/occlusion if desired. Doppler, rolloff factor, underwater low-pass and the wind generator (~170 lines of DSP) are all straightforward to port; the FMOD-only internet streaming needs an HTTP/ICY client (`reqwest` streaming body) + `symphonia` (MP3/AAC/Vorbis/Opus) -- that is the part with the most new code. Verdict: **pure Rust is realistic**; FMOD brings nothing the new viewer cannot do with `kira`/`oddio` + `symphonia`, and removing it removes the only proprietary runtime in the audio path.

## 3. How much C++ is necessary for shaders

**Confirmed: the viewer compiles GLSL at runtime through the GL driver only.** `LLShaderMgr::loadShaderFile` reads each `.glsl` file, synthesises a preamble, and calls `glShaderSource`/`glCompileShader` (`indra/llrender/llshadermgr.cpp:874-889`); programs are linked with `glLinkProgram` (`:962`). There is no offline shader tooling anywhere in the tree: no glslang/shaderc/glslc/SPIR-V references in any `.cmake`, `CMakeLists.txt`, `.py` or `.sh` (grep returned nothing). The only cache is of **driver program binaries** (`glGetProgramBinary`) keyed by a UUID of the assembled source, stored under `cache/shader_cache` with LLSD metadata (`llshadermgr.cpp:1009-1129`), enabled only on GL >= 4.1 (`:1014`).

Shader corpus: 224 `.glsl` files, 25,320 lines under `indra/newview/app_settings/shaders/class{1,2,3}/{avatar,deferred,effects,environment,gltf,interface,lighting,objects,post,windlight}`.

### How a program's source is assembled at runtime

1. A `#version` line chosen from the driver's reported GLSL level: 420 / 400 / 330 / 150 / 140 (`llshadermgr.cpp:569-617`).
2. `#define FRAGMENT_SHADER 1` or `VERTEX_SHADER 1`, G-buffer flag constants (`:627-640`).
3. Every entry of the program's `mDefines` map as `#define KEY VALUE` (`:642-648`) -- these are the "permutations".
4. Hardware-conditional defines: `IS_AMD_CARD` (`:653`), `OLD_SELECT` on non-Apple (`:467-469`).
5. For fragment shaders with indexed texturing, a generated `diffuseLookup()` with N `uniform sampler2D texN` declarations and either a `switch` or an NVIDIA-specific `if/else` chain, where N = `texture_index_channels` (hardware-dependent, `:655-738`).
6. The `GBufferInfo` struct text (`:741`).
7. The file body, split at an "extra block" marker so defines land after the file's own `#extension` lines (`:744-760`).
8. Separately, **feature snippets**: `attachShaderFeatures` (`llshadermgr.cpp:68-460`) attaches up to 34 shared `.glsl` objects (atmospherics, lighting, shadows, SSAO, reflection probes, tonemap, PBR terrain, skinning, ...) based on 21 boolean `LLShaderFeatures` flags.
9. Class fallback: if compilation fails at class N, the file is retried from `classN-1/` (`llshadermgr.cpp:941-946`).

### Variant count

Program objects declared in `indra/newview/llviewershadermgr.cpp`: 149 distinct global `LLGLSLShader` names, of which 9 are arrays: `gDeferredMaterialProgram[32]` (16 material modes x rigged, `llviewershadermgr.cpp:1302-1372`, defines `HAS_NORMAL_MAP`/`HAS_SPECULAR_MAP`/`DIFFUSE_ALPHA_MODE 0-3`/`HAS_ALPHA_MASK`/`HAS_SKIN`), `gDeferredMultiLightProgram[16]` (`LIGHT_COUNT` 1..16, `:1115`), `gFXAAProgram[4]` + 3 x `gSMAA*Program[4]` (quality presets), `gDeferredPBRTerrainProgram[TERRAIN_PAINT_TYPE_COUNT]`, `gNormalDebugProgram[..]`, plus `gGLTFPBRMetallicRoughnessProgram.mGLTFVariants[16]` (bits `ALPHA_BLEND|RIGGED|UNLIT|MULTI_UV`, `indra/llrender/llglslshader.h:347-355`, built by `make_gltf_variants` `:352-370`). Rigged variants are produced systematically by `make_rigged_variant` (`:251-263`, 5 explicit + the material/GLTF arrays). **Roughly 220-230 linked programs are resident for one settings configuration.** `createShader(` is called 129 times textually plus the loops.

Setting-driven defines that trigger a full reload when changed (`addPermutation` sites, 94 total, 46 distinct keys): `HAS_SUN_SHADOW` (RenderShadowDetail; 8 sites), `HAS_SSAO`, `HERO_PROBES` (RenderMirrors), `TRANSPARENT_WATER`, `HAS_HDRI`, `HAS_NOISE` (RenderGlowNoise), `AVATAR_CLOTH`, `GAMMA_CORRECT`/`LEGACY_GAMMA`/`NO_POST` (post-pipeline branches), `PROBE_FILTER_SAMPLES` (RenderReflectionProbeLevel), `TERRAIN_PBR_DETAIL` (5 levels), `TERRAIN_PLANAR_TEXTURE_SAMPLE_COUNT` (1|3), `TERRAIN_PAINT_TYPE`, `TERRAIN_PAINT_PRECISION`, `FXAA_QUALITY__PRESET`. Hardware-derived defines: `MAX_UBO_VEC4S`, `MAX_NODES_PER_GLTF_OBJECT`, `MAX_MATERIALS_PER_GLTF_OBJECT` computed from `GL_MAX_UNIFORM_BLOCK_SIZE` (`llviewershadermgr.cpp:289-299`), `DEPTH_CLAMP`, `FXAA_GLSL_130/400`, the `#version`, `IS_AMD_CARD`, `OLD_SELECT`, and the indexed-texture channel count.

Multiplying only the settings-driven binary toggles that touch the deferred core (shadows x SSAO x hero probes x HDRI x transparent water = 2^5) over ~220 programs gives ~7,000 program variants; adding terrain (5x2x2), AA presets and the hardware-derived constants pushes a *complete* offline matrix past 10^4, and the hardware-derived UBO constants make it unbounded unless they become specialization constants or UBO arrays sized by a push constant.

Honest answer to "how much C++ is necessary for shaders": **zero C++ in the viewer's own code**, but if you want to keep compiling GLSL at runtime you ship glslang (C++) through a Rust crate. Naga can replace it only after a preprocessing layer and shader clean-up; offline-only compilation requires re-architecting the variant system around specialization constants. The variant explosion is real but mostly *settings-level*, so the practical set a user ever compiles in one session is a few hundred programs, not thousands -- which is why the runtime model has worked for LL.

## 4. The out-of-process plugin architecture (llplugin + media_plugins)

What it does (`indra/llplugin/`, 7,076 lines; `indra/media_plugins/`, 7,410 lines):

- The viewer (`LLPluginProcessParent`, `indra/llplugin/llpluginprocessparent.cpp`) opens a TCP listen socket on 127.0.0.1 (`:419`; FS binds a fixed port because some drivers misreport ephemeral ports, `llpluginprocessparent.h:215`), spawns `SLPlugin[.exe]` with that port as its only argument (`indra/llplugin/slplugin/slplugin.cpp:153-173`; `add_executable(SLPlugin` at `slplugin/CMakeLists.txt:27`), and walks a state machine `STATE_LISTENING -> LAUNCHED -> CONNECTED -> HELLO -> LOADING -> RUNNING -> GOODBYE/EXITING` (`llpluginprocessparent.h:136-151`).
- `SLPlugin` (`LLPluginProcessChild`) connects back (`indra/llplugin/llpluginprocesschild.cpp:75`), receives `load_plugin` naming a shared library (`media_plugin_cef.dll`, `media_plugin_libvlc.dll`, `libmedia_plugin_gstreamer.so`), `dlopen`s it with APR (`indra/llplugin/llplugininstance.cpp:98-112`) and calls `init_media_plugin` (`indra/media_plugins/base/media_plugin_base.h:123-126`).
- Messages are **LLSD maps serialised as LLSD-XML strings, NUL-delimited on the socket** (`indra/llplugin/llpluginmessagepipe.cpp:36,125`; `LLPluginMessage::generate/parse`, `llpluginmessage.h`), grouped by class: `internal`, `base`, `media`, `media_browser`, `media_time` (`llpluginmessageclasses.h:38-51`). `LLPluginClassMedia` (1,670 lines) is the viewer-side typed facade (navigate, mouse/key events, size, volume, cookies, auth, JS dialogs, file pickers...).
- Pixels travel through **shared memory** segments (APR shm on Windows, `shm_open`/`mmap` on POSIX, `indra/llplugin/llpluginsharedmemory.cpp:33-359`); the CEF plugin `memcpy`s each repaint into the segment and sends a dirty rect (`indra/media_plugins/cef/media_plugin_cef.cpp:198-210`); the viewer uploads the dirty rect into the media texture (`indra/newview/llviewermedia.cpp:3148`).
- Heartbeats with a 15 s lockup timeout (`llpluginprocessparent.cpp:107,781`), sleep-time throttling for background media (`:753-763`), per-process CPU accounting, and a `MEDIA_EVENT_PLUGIN_FAILED` path that lets the viewer survive a plugin crash (`llviewermedia.cpp:3449-3454`).
- Platform extras: per-plugin audio volume capture (`windows_volume_catcher.cpp` via `mmeapi`, `linux_volume_catcher.cpp` via PulseAudio introspection, `mac_volume_catcher.cpp`), a Linux `chrome-sandbox` suid helper check (`llviewermedia.cpp:1810-1818`), a macOS Cocoa shim (`slplugin-objc.mm`).

Why: isolation of CEF/Chromium (and VLC/GStreamer) from the viewer process -- crash containment, memory containment (Chromium's multi-process model already spawns its own helpers; CEF must initialise on the main thread of its process and conflicts with the viewer's own message loop and GL context), licence/ABI separation (GPL libvlc, LGPL GStreamer), and the ability to kill/restart a hung plugin. The design predates CEF (it was built for the Mozilla/LLQtWebKit era, 2008-2010 copyright headers) and has stayed because every one of those reasons still holds.

Would a Rust viewer need the same? **Yes, for CEF.** CEF's process model, main-thread requirement, 150 MB of DLLs and crash surface make in-process embedding in a Vulkan game loop unattractive; `cef-rs` still expects to own a process. The simplest port: keep the *protocol* idea (child process, LLSD-or-protobuf messages over a local socket or pipe, shared memory for frames) but implement the host side in Rust (`tokio` + `interprocess`/`shared_memory`) and the child in Rust using `cef-rs`, or keep the existing C++ `SLPlugin`+`media_plugin_cef` unchanged as a sidecar and only re-implement `LLPluginProcessParent`/`LLPluginClassMedia` in Rust (that is ~3,500 lines of C++ to replace, and it buys you the Dullahan/CEF work for free). For audio/video media (libVLC/GStreamer) an in-process `gstreamer-rs` pipeline is viable and would remove two of the three plugins, but keeping them out-of-process for licence hygiene (GPL libvlc) and crash isolation is defensible. Under Vulkan you also gain the option of sharing the frame via an external memory handle (`VK_KHR_external_memory_win32`/fd) instead of CPU `memcpy` + texture upload.

## 6. Closing estimate: FFI versus pure Rust

### Pure Rust (no C/C++ at all)
- Networking/HTTP/TLS: `reqwest`/`hyper`/`rustls`, raw UDP via `tokio::net::UdpSocket`. (replaces curl, openssl, nghttp2, apr)
- Compression: `flate2`, `zstd`. (zlib-ng)
- Images: `png`, `zune-jpeg`/`jpeg-encoder`, `exr`, own TGA/BMP/DXT-container readers (~1k lines). (libpng, libjpeg-turbo, tinyexr)
- XML/LLSD/JSON: `quick-xml`, own LLSD codecs, `serde_json`. (expat, boost::json; XML-RPC login is implemented in-tree on top of LLXMLNode -- `indra/newview/llxmlrpctransaction.cpp:45` -- so no xmlrpc-epi dependency exists to replace; ~1.2k lines to port)
- Math: `glam`. (glm, glh, llmath vector classes)
- Tangents: `mikktspace` (Bevy port). Hashing: `xxhash-rust`. UUID: `uuid`.
- Fonts/text: `cosmic-text` (+ `resvg` for SVG emoji). (freetype, nanosvg, fontconfig)
- Windowing/input/dialogs/clipboard/notifications: `winit`, `rfd`, `arboard`, `notify-rust`. (SDL2, FLTK, Growl, libnotify, Win32/Cocoa/X11 code)
- Audio: `kira` or `oddio` + `cpal`, `lewton`/`symphonia` for decode. (FMOD, OpenAL, alut, libvorbis decode)
- Crash reporting/profiling/updates: `minidumper`+`crash-handler`, `tracy-client`, `velopack`. (BugSplat, breakpad, Tracy C++, Velopack C lib)
- Discord: `discord-rich-presence`. Physics decomposition: pure-Rust VHACD port if acceptable, else FFI.
- All viewer logic: llmath/LLVolume, llmessage, LLSD, llprimitive, llcharacter, llappearance, llinventory, settings, caps, renderer, UI.

### FFI to C/C++ (pragmatic, at least initially)
1. **JPEG2000 (OpenJPEG)** -- texture decode is the single most performance-critical codec in SL and needs resolution-reduced + truncated-stream decoding plus encoding; pure-Rust options are decode-only and immature. API surface used today: ~45 `opj_*` functions/types (`indra/llimagej2coj/llimagej2coj.cpp`). FFI via `openjp2-sys`. Keep an eye on `jpeg2000-decoder`/`openjp2` (c2rust) for a later swap. (KDU is dropped: proprietary, no bindings.)
2. **libwebrtc** -- for SL voice parity (AEC/AGC/NS, device I/O, NetEQ, Opus). API surface: the 60 `webrtc::` symbols used by `llwebrtc.cpp`, i.e. PeerConnectionFactory, PeerConnection, AudioDeviceModule, AudioProcessing, DataChannel, stats. Use `webrtc-sys` (LiveKit) or wrap `llwebrtc.dll`'s existing C++ interface (`indra/llwebrtc/llwebrtc.h`, ~25 virtuals) behind a C ABI -- that DLL is already a clean boundary. Alternative later: `webrtc-rs` + own audio processing.
3. **CEF** -- unavoidable C++ (Chromium); via `cef-rs` or the existing Dullahan/`SLPlugin` sidecar process. 60 Dullahan entry points today. Lives out of process either way.
4. **Media playback** -- `gstreamer-rs` is Rust bindings over the C GStreamer runtime (LGPL, dynamic); or `vlc-rs` over libvlc. Either is "FFI" in the sense of shipping C libraries, but the bindings are mature.
5. **Shader compiler** -- glslang/SPIRV-Tools via `shaderc`/`glslang` crates if runtime GLSL compilation is kept (section 3). Build-time C++ only.
6. **meshoptimizer** -- `meshopt` crate is FFI to the C++ library; 9 functions used. Mature; no reason to port.
7. **Vorbis encode** (uploads only) -- `vorbis_rs` FFI, or defer the feature.
8. **Hunspell** -- `hunspell-rs` FFI unless `spellbook` proves adequate.
9. **Vivox** (OpenSim grids only) -- external `SLVoice` daemon spoken to over TCP; not linked, just launched. The C++ client (`llvoicevivox.cpp`, 8k lines) needs porting if OpenSim voice is in scope.
10. **VHACD** -- FFI (`vhacd-sys`) is the safe choice for mesh-upload physics; upload-only, low risk.
11. **3Dconnexion** -- `libndofdev` FFI or `hidapi`; optional.

### FFI surface-area estimate
- Mandatory C/C++ libraries in the shipped Rust viewer: **3** (OpenJPEG, libwebrtc, CEF) plus **1-2 media runtimes** (GStreamer and/or libvlc, out of process) and **meshoptimizer** (tiny). Optional: glslang (build-time or runtime), hunspell, libvorbis (encode), VHACD, libndofdev.
- Approximate API size to bind or wrap: OpenJPEG ~45 symbols; libwebrtc ~60 classes/functions (or ~25 virtuals if you keep `llwebrtc` as a C++ shim with a C ABI); Dullahan/CEF ~60 methods + ~20 callbacks (or zero if the C++ sidecar is reused verbatim and only the LLSD-over-socket protocol is reimplemented, which is the cheapest path); GStreamer via `gstreamer-rs` (no manual binding); meshoptimizer 9 functions; glslang via `shaderc` (no manual binding). Total hand-written `unsafe` binding/wrapper code: on the order of 2-4k lines, concentrated in J2C and voice.
- Proprietary components that disappear in the Rust viewer: FMOD Studio, Kakadu, Havok (`llphysicsextensions_tpv`), BugSplat, Vivox (SL grid), LL's Discord SDK. The remaining non-OSI pieces are CEF (BSD), GStreamer/libvlc (LGPL/GPL, out of process), and Steam Audio if HRTF is wanted (free binary, not OSI).
